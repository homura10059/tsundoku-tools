# 要件定義書：Amazon Kindleウィッシュリスト自動監視システム

## 1. 目的と概要
本システムは、Amazonの公開ウィッシュリストを定期的に自動巡回し、Kindle（電子書籍）の価格・ポイント還元率を監視する。紙の書籍の定価（基準価格）と比較して、割引またはポイント還元によって**実質20%以上お得になった商品**を検知し、Discordへ一括通知することで、セールの見落としを防ぎ購入の自動判断を支援することを目的とする。

---

## 2. システム要件

### 2.1. 監視対象・トリガー要件
* **対象リスト:** 公開設定されたAmazonのほしい物リスト（URL指定 / ログイン不要）。**複数リストを登録でき、リストごとに有効／無効を切り替えられる。**
* **設定の永続化:** 監視対象リスト（URL・表示名・判定閾値・有効フラグ）は **Cloudflare D1** の `wishlists` テーブルで管理し、コード変更や Secrets 変更なしに増減できること。
    * *※Discord Webhook URL や API トークンなどのシークレットは D1 に置かず、環境変数から読む。*
* **対象商品:** リスト内の **Kindle（電子書籍）のみ**。
    * *※Kindle Unlimited（読み放題）対象化は購入ではないため監視対象外とする。*
    * *※電子書籍のため、在庫切れや送料の概念は考慮しない。*
* **実行頻度:** 1日1回（定期実行）。
* **アーキテクチャ分離:** 定期実行スケジュール（トリガー部）と、クローラー・通知ロジック（実行部）を明確に分離し、開発時や任意のタイミングで**即座に手動実行できる仕組み**を担保する。

### 2.2. データ取得・クローリング要件
* **無限スクロール対応:** ログインなしのウィッシュリスト画面において、全商品（最大100件程度を想定）がロードされるまで最下部へのスクロールをシミュレートしてデータを網羅する。
* **負荷軽減・Bot検知回避（ジッター）:** * Amazonからのアクセスブロック（CAPTCHA等）を避けるため、ページ遷移やデータ処理の間に **1.0秒〜3.0秒のランダムな待ち時間（ジッター）** を挿入する。
    * ヘッドレスブラウザのUser-Agentおよびロケール（ja-JP）を適切に偽装する。

### 2.3. 判定ロジック要件
各商品のデータから以下を抽出し、判定式を満たした場合にのみ通知対象とする。
* **基準価格 ($P_{base}$):** 「単行本（紙）」または「定価/参考価格」
* **Kindle価格 ($P_{kindle}$):** 現在のKindle販売価格
* **付与ポイント ($Pt$):** 商品ページに明示されているポイント（期間限定ポイントを含む）
    * *※「まとめ買いキャンペーン」等のカート内でのみ適用される特殊な割引は考慮しない。*

$$\text{判定条件:} \quad \left( \frac{P_{base} - P_{kindle}}{P_{base}} \ge \theta \right) \quad \text{または} \quad \left( \frac{Pt}{P_{base}} \ge \theta \right)$$

* **閾値 ($\theta$):** リスト単位に設定できる（`wishlists.threshold`）。未設定の場合の既定値は **0.20**。

### 2.4. 通知要件
* **通知先:** Discord（Webhook経由）。
* **ステートレス運用（重複通知の許容）:** **通知の判断に過去の状態を使わない。** セール状態が継続している場合、毎日同じ商品が通知されてもよいものとする。
    * *※増分8以降、巡回結果は D1 に観測ログとして蓄積されるが、これは価格推移の分析と抽出ロジック劣化の遡及調査のためであり、通知の判断（重複抑制・値下がり検知）には使わない。観測ログは180日保持し、実行末尾で古い行を削除する。D1への書き込みに失敗しても警告ログのみで通知は継続する（exit codeは変えない）。*
* **バッファリング（分割送信）:** * Discordの文字数制限（1メッセージ2,000文字）およびレートリミットを回避するため、ヒットした商品は **5件ごとに1つのメッセージ（Embed形式）に集約して分割送信** する。
    * 分割送信の間には最低2秒のウェイトを挟む。
* **通知内容:** 「本のタイトル」「現在のKindle価格」「割引率またはポイント還元率」「商品へのAmazonリンク」

## 3. 技術スタック
* **言語:** TypeScript (Node.js)
* **主要ライブラリ:** Playwright (ブラウザ自動操縦およびデータ抽出)
* **データストア:** Cloudflare D1（設定および観測ログ）
    * *※実行部は Playwright を必要とするため Node 上で動く。D1 のバインディングは Workers 専用なので、D1 へは REST API でアクセスする。*
* **実行インフラ:** 制限なし（GitHub Actions、ローカル環境、またはVPS等の環境でポータブルに動作すること）

## 4. DoD（Definition of Done：完了定義）

本プロジェクトの開発・実装フェーズは、以下の基準をすべて満たした時点で「完了（Done）」と定義する。

### 🟩 4.1. 機能検証（Functionality）
- [ ] **全件ロードの検証:** 100件以上の商品が登録された公開ウィッシュリストを入力した際、無限スクロールが最後まで作動し、全件を取りこぼさずパースできていること。
- [ ] **判定ロジックの正確性:** 「割引のみ20%以上」「ポイントのみ20%以上」「両方合算（ただし各々20%未満）」のダミーデータを用いてテストし、要件通りの条件でのみトリガーされること。
- [ ] **バッファリングの検証:** セール対象品が11件以上ヒットした際、Discordへ5件・5件・1件のように適切に分割され、レートリミットエラー（429 Too Many Requests）を起こさずにすべてのメッセージが届くこと。
- [ ] **実行の分離:** 定期実行の仕組みとは別に、ローカルのCLIまたはGitHubの画面から「今すぐ実行」を叩いて即時に通知が届くことが確認できていること。

### 🟩 4.2. 運用・堅牢性（Robustness）
- [ ] **エラーハンドリング:** リスト内にKindle以外の形式（紙の書籍のみ、ガジェット等）が混在していた場合、または特定のアイテムのパースに失敗した場合でも、システムがクラッシュせず、エラーをログに出力して次の商品の処理を継続できること。
- [ ] **環境変数の秘匿:** AmazonのウィッシュリストURLやDiscordのWebhook URLがコード内にハードコードされておらず、環境変数（`.env` または GitHub Secrets）から安全に読み込まれていること。

### 🟩 4.3. コード品質（Code Quality）
- [ ] **型安全性の担保:** `any` 型を極力排除し、スクレイピングデータや通知オブジェクトにTypeScriptの型定義（Interface/Type）が正しく適用されていること。
- [ ] **再現性の確保:** `package.json` およびパッケージロックファイルが整備され、別の環境（CI環境など）でも `npm ci` のみで必要な依存関係（Playwrightのブラウザバイナリ含む）が過不足なくセットアップできること。
